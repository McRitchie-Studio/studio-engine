- **The engine's own tables meet the hub's database standard.** Two new migrations, for every host. `RequireSlugsOnEngineTables` makes `slug` NOT NULL with a unique index on `error_logs`, `theme_settings`, `studio_geo_settings` and `studio_site_identities`. It first fills a NULL or blank slug the way the model writes one (`error-log-<id>`, `theme-<app>`, `geo-<app>`, `site-identity-<app>`), and gives a duplicate after the first `-<id>`. `AddEngineStateChecks` adds CHECK `studio_links_kind_known` (`Studio::LinkToken::KINDS`) and `studio_knowledge_docs_status_known` (`Studio::KnowledgeDoc::STATUSES`), and stops with the stray values named if a row holds another value. Production held no NULL slug, no duplicate and no stray value on 2026-11-08. `ErrorLog` now includes `Sluggable`, so a bare `ErrorLog.create!` gets `error-log-<id>` too, and a host's own `update_column(:slug, "error-log-#{log.id}")` after a create may go. To adopt, use two releases, model first. Release one bumps the gem only: the new `ErrorLog` writes a slug on the old nullable column. Release two runs `bin/rails studio_engine:install:migrations && bin/rails db:migrate` and commits `db/schema.rb`. In one release, old dynos insert a NULL slug until the restart, and a failed release or a `heroku rollback` leaves old code on the NOT NULL column, so every `ErrorLog` write fails; undo it with `bin/rails db:migrate:down VERSION=20261108160000` before the rollback. A host whose own state registry lists `studio_knowledge_docs.status` as unconstrained (the hub's `StringStates`) moves it to a checked entry.
